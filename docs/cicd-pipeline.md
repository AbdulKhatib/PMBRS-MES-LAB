# PMBRS — CI/CD Pipeline (Stage 6)

## Summary

A gated BUILD → TEST → DEPLOY → VERIFY pipeline was built to automate deployment of the PMBRS Flask application to IIS, carrying forward the exit-code discipline established in an earlier hands-on lab: every stage must explicitly signal pass or fail via `errorlevel`, and the orchestrator stops immediately on the first failure rather than proceeding regardless of stage outcome.

This pipeline also absorbs the deployment-automation responsibility originally scoped as a separate step (installing/copying application files to IIS) — folded into the DEPLOY stage rather than built as a standalone script, since the manual deployment process was already proven working by hand during Stage 4 and a second, separate script would have duplicated that logic rather than adding coverage.

## Design

```
BUILD
  - confirms required application files exist (app.py, web.config, config.py)
  - confirms Python is available on PATH
  |
  v
TEST
  - confirms IIS service (W3SVC) is running
  - calls the running application's /health endpoint
  - checks the response confirms both application and database are OK
  |
  v
DEPLOY
  - backs up the currently live app.py before overwriting it
  - copies the validated source files from C:\PMBRS\application\ to the live IIS site
  - recycles the application pool to force IIS to load the new code
  |
  v
VERIFY
  - re-calls /health against the now-live deployment
  - confirms HTTP 200 and a fresh "database": "OK" response
```

Each stage is a standalone script (`build.bat`, `test.bat`, `deploy.bat`, `verify.bat`) that can be run independently for debugging, orchestrated together by `pipeline.bat`, which calls each in sequence and checks `errorlevel` immediately after each call.

Source of truth: `C:\PMBRS\application\` (validated by BUILD, copied by DEPLOY).
Live deployment target: `C:\inetpub\wwwroot\pmbrs\` (the actual IIS site).

Full scripts are in `/deployment/`.

## Verification

A full pipeline run completed successfully end to end:

```
BUILD       PASS
TEST        PASS
DEPLOY      PASS
VERIFY      PASS
PIPELINE: SUCCESS
```

This was not the first run — two real defects in the pipeline itself were found and fixed first (below), both caught because a FAIL result was investigated rather than dismissed or worked around.

## Incidents

### 1. TEST stage false failure — JSON format mismatch

**Observed:** TEST stage reported "Application health check did not return OK" despite the application actually being healthy.

**Investigation:** Rather than assume the application was broken, the raw `/health` response was read directly (`type response.json`) before trusting the script's verdict. It showed `{"application":"OK","database":"OK","version":"1.0.0"}` — genuinely healthy.

**Root cause:** The `findstr` pattern checked for `"application": "OK"` with a space after the colon. Flask's default `jsonify` output has no space after the colon. The exact-match check was looking for a format the application never actually produces.

**Resolution:** Adjusted the `findstr` patterns in `test.bat` to match the actual no-space JSON format.

**Lesson:** An automated check reporting FAIL is not proof the system under test is broken — it may be the check itself that's wrong. Verifying the raw output before trusting the script's summary caught this immediately rather than triggering an unnecessary and incorrect rollback investigation.

### 2. VERIFY stage checking the wrong file

**Observed:** Not yet surfaced as a visible failure at the time it was found — caught by code review while fixing incident #1.

**Root cause:** `verify.bat` saves its curl output to `verify_response.json`, but its `findstr` check was reading from `response.json` — a different file, left over from the TEST stage's own run. Depending on execution order and leftover state, this check could pass against stale data or fail against a missing file, without ever actually validating VERIFY's own fresh response.

**Resolution:** Corrected the `findstr` target to `verify_response.json`, matching the file VERIFY actually writes.

**Lesson:** Copy-pasting a check pattern between similar stages is a real risk of silently checking the wrong thing. Each stage's validation should be reviewed against what that specific stage actually produces, not assumed correct because a similar stage's version worked.

## Files Excluded from Version Control

`deployment/deployment.log` and `deployment/*.backup` are excluded via `.gitignore`. The log is runtime output that changes on every pipeline execution — not meaningful commit history. The backup file is a deployment artifact generated by DEPLOY, not source content.
