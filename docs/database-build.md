# PMBRS — Database Build (Stage 3)

## Summary

Oracle Database 21c Express Edition was installed on the DB tier (mes-lab-vm), the PMBRS schema was built inside the pluggable database (XEPDB1), populated with seed data, and verified with a set of test queries. The build surfaced several real configuration and resourcing issues, documented below as incidents rather than omitted.

## Install

- Oracle Database 21c XE for Windows, downloaded from Oracle's official distribution
- Installed on Windows Server 2022 (mes-lab-vm)
- Default listener port: 1521
- Default pluggable database: XEPDB1

## Schema

Five tables were created inside XEPDB1, under a dedicated application user (`pmbrs_app`) rather than the default SYS/SYSTEM accounts, in line with least-privilege practice:

- `batch_status` — reference/lookup table for controlled batch status values
- `equipment` — fictional manufacturing equipment and status
- `batch` — production batches, foreign-keyed to equipment and batch_status
- `production_event` — events tied to a batch and/or equipment
- `audit_event` — application-level audit log

Constraints applied: primary keys (via `GENERATED BY DEFAULT AS IDENTITY`), foreign keys linking batch/equipment/events, one check constraint on batch start/end time ordering, and two indexes supporting the most common join paths.

Seed data: 5 batch statuses, 3 equipment records, 3 batches, 2 production events — sufficient to exercise every relationship and support the verification queries below.

Full SQL is in `/database/01_schema.sql` through `/database/05_queries.sql`.

## Verification

Three queries were run against the seeded data and confirmed correct:
- Active batches — returned the one batch seeded as ACTIVE
- Failed batch joined to its production event — correctly matched BATCH-1003 to its equipment-fault event
- Batch count grouped by equipment — correctly showed one batch per equipment record

## Incidents

### 1. ORA-12541: TNS:no listener (first connection attempt)

**Observed:** Immediately after install, the first `sqlplus` connection attempt failed with "no listener."

**Investigation:** Checked Windows Services (`services.msc`) — both `OracleServiceXE` and `OracleXETNSListener` were in a Stopped state despite the install completing successfully.

**Root cause:** The installer did not automatically start both services on this environment.

**Resolution:** Manually started both services and set their startup type to Automatic, so they would persist across any future instance reboot.

### 2. Oracle instability on undersized instance (t3.small, 2GB RAM)

**Observed:** The listener came up successfully after the fix above, but a subsequent connection attempt several minutes later failed again with the same ORA-12541 error, with no user action in between.

**Investigation:** Task Manager showed memory at 95% utilization (1.9GB of 2.0GB) with Oracle actively running, and the system's commit charge close to its limit.

**Root cause:** Oracle 21c XE's recommended minimum is 4GB RAM; the instance was provisioned at 2GB (t3.small). Under normal idle load, this was enough memory pressure to destabilize the Oracle services.

**Resolution:** Resized the instance. t3.medium was unavailable in this AZ (us-east-2b) at the time of resizing, so the instance was moved to m7i-flex.large (8GB RAM) instead. Stable since.

### 3. ORA-00922: missing or invalid option (password syntax)

**Observed:** `CREATE USER pmbrs_app IDENTIFIED BY <password with special character>` failed to parse.

**Root cause:** An unescaped `!` character in the password literal broke SQL*Plus's parser. Oracle requires special characters in `IDENTIFIED BY` clauses to be quoted.

**Resolution:** Removed the special character from the password rather than quoting it, to avoid the same issue recurring anywhere else the password is used (application config, connection strings).

### 4. ORA-65096: invalid common user or role name

**Observed:** After fixing the password syntax, `CREATE USER` still failed, this time with a multitenant-specific error.

**Root cause:** The connection was against the CDB root container (service name `XE`), not the pluggable database. Oracle's multitenant architecture restricts regular (non-common) user creation to within a PDB.

**Resolution:** Reconnected using the PDB service name (`XEPDB1` instead of `XE`) and reran the script successfully. This distinction — CDB root vs. PDB — must be applied consistently to every subsequent connection, including the application's connection string.

### 5. HTTP 500.19 / 500.0 — see `iis-build.md`

Encountered during the application build, not the database build, but caused by a related pattern: default IIS/Windows configuration locking down access that application code assumes is open. Documented in full in `iis-build.md`.

## Password Handling

The SYS and application-user (`pmbrs_app`) passwords are intentionally not recorded in this document or committed to the repository. The application's database credentials are stored in `application/config.py`, which is excluded via `.gitignore`; `application/config.example.py` documents the required structure without real values.
